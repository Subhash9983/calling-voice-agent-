## Doc-conformance table — five flagged items

### 1. Doc conflict: docs/02 §5 requires `transport.credential_ref`; docs/12 §9 makes LiveKit keys bootstrap-only

**Finding confirmed as a genuine conflict between two approved docs**, not a code defect. docs/02 §5 lists `credential_ref` as a required embedded `transport` field with no stated exception. docs/12 §9 is explicit and unambiguous: "`MONGODB_URI`, `LIVEKIT_API_KEY` and `LIVEKIT_API_SECRET` are bootstrap-only ... and cannot be selected through a `credential_ref`."

The implementation reconciles this without violating either document's *security* intent: `provider_registry/approved.py` defines `LIVEKIT_RECORDED_CREDENTIAL_REF = "env:LIVEKIT_API_KEY"` as the only accepted value for `transport.credential_ref` when `provider == "livekit"` (satisfying docs/02's structural "required field" requirement), while `security/credentials.py`'s `RESOLVABLE_CREDENTIAL_NAMES` allowlist excludes the LiveKit names entirely and `parse_credential_ref`/`CredentialResolver.resolve` raise `CREDENTIAL_REF_NOT_ALLOWED` for any attempt to resolve it (satisfying docs/12's "never resolvable" requirement). This is recorded as evidence only, never resolved to a value.

**Recommendation:** accept this as correct and safe for Phase 0 — it does not leak a value or grant an unapproved resolution path either way. However, the conflict is real (not silent-reasonable extrapolation but two docs literally disagreeing on whether the field is required-and-resolvable vs. bootstrap-only-and-unresolvable), so it should be closed with a documentation amendment rather than left as inline code commentary: either (a) amend docs/02 §5 to state the transport `credential_ref` is a recorded-evidence-only field for the `livekit` provider, unresolvable via `CredentialResolver`, or (b) amend docs/12 §9 to carve out an explicit "recorded but unresolvable" exception. This is a MEDIUM-priority documentation debt item for the orchestrator/user to decide and formally amend, not a blocking WP3 defect since the code already implements the safer of the two readings.

### 2. New `frontend/src/config/` directory not in docs/14 §4 layout

docs/14 §4's enumerated `frontend/src/` subdirectories are `api/, audio/, components/, contracts/, livekit/, session/, telemetry/` — `config/` is not listed. However, §4's actual restrictive rule is "no additional **service/package root** is introduced without a demonstrated need and approval," which is about new top-level applications/services, not about adding a focused subdirectory under an existing `src/` tree to satisfy a different, later-authored spec (docs/12 §11, whose "Implementation status" was "Not started" when docs/14 §4's list was written).

**Recommendation:** SILENT-REASONABLE, not a defect. `config/` is minimal (3 files, ~250 lines including tests), single-purpose (the "only place application code may read build-time environment configuration," per its own docstring), and necessary to satisfy docs/12 §11-12's browser-public-configuration gate, which docs/14 §9's WP3 deliverables explicitly require ("enforce the approved ... public/private configuration split"). Recommend the orchestrator update docs/14 §4's list to add `config/` for documentation accuracy, but this does not block the gate.

### 3. `VITE_APP_ENV` restricted to `development|rd`

docs/12 §11 gives only an example value (`VITE_APP_ENV=development`) and does not itself enumerate the full allowed set for the *browser-public* field; docs/12 §6 sets `development|rd` (production rejected) for the *server-side* `APP_ENV`. The frontend's `PUBLIC_APP_ENV_VALUES = ["development", "rd"]` mirrors the backend's Phase 0 boundary.

**Recommendation:** CONFORMS by reasonable extension — consistent with the Phase-0-wide "production is rejected" rule stated repeatedly across docs/12 (§6, §19 "browser-selectable provider credentials/configuration" exclusions) and with keeping the browser and backend environment labels in lockstep so a build cannot silently claim a `production` label the backend would reject. Not a defect; optionally worth a one-line docs/12 §11 amendment stating the same enum explicitly for the browser field, for documentation completeness only.

### 4. Added `turn_handling.vad` sub-object not in docs/02

docs/02 §5's literal "Embedded `turn_handling` fields" list (`mode`, `interruptions_enabled`, `interruption_mode`, `minimum_interruption_ms`, `minimum_endpointing_ms`, `maximum_endpointing_ms`, `false_interruption_suppression`, `preemptive_generation`) does not mention a `vad` sub-object. However, docs/12 §7 explicitly names `vad.playback_activation_threshold` (default `0.7`) as a "named speech-activity key" belonging to the immutable `agent_config`, and docs/02 §5 itself says timeout/retry values are approved in "Section 24" while provider-specific option schemas remain "separately approved per adapter" — i.e., docs/02's list was not asserted to be the final closed set of every nested field.

**Recommendation:** SILENT-REASONABLE / CONFORMS-to-docs/12. The code (`domain/agent_config.py`'s `VadSection`, nested at `turn_handling.vad`) is the only place in the schema that can house the exact key name docs/12 §7 mandates (`vad.playback_activation_threshold`), and its validated defaults (`activation_threshold=0.5`, `playback_activation_threshold=0.7`, ordering-enforced) match docs/12 §7's stated values exactly. Recommend closing this by amending docs/02 §5 to add `vad` to the documented `turn_handling` embedded-field list (a documentation-completeness fix), not a code change.

### 5. Unknown `APP_*`/`VOICE_AGENT_*` env vars block startup

This directly implements docs/12 §3's explicit requirement: "unknown or misspelled settings rejected where the selected source supports detection." `config_loader._environment_values` rejects any `APP_`/`VOICE_AGENT_`-prefixed environment variable that is not in the exact `SETTING_ALIASES` set, via `ConfigReason.SETTING_UNKNOWN`.

**Recommendation:** CONFORMS. No action needed. This is precisely the fail-safe, typo-catching behaviour the spec calls for, and it is scoped only to the two prefixes this application owns (it does not reject arbitrary unrelated environment variables the host process may have set for unrelated tooling).
