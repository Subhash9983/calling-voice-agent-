## Deferred items — assessed as correctly scoped for WP4, not defects

1. **Reconciler not built; `ending` sessions never automatically finalize.** Correct scope: docs/14 §10 assigns the reconciler to a later WP (referenced from WP5/§9's "nonterminal session reconciliation indexes" and WP9-10's worker lifecycle); WP4's own exit gate only requires the *request* to be idempotent and durable, which it is (`request_end` records the authoritative `termination_request` and transitions to `ending` exactly once). Not a WP4 defect.
2. **Reconnect window not enforced.** `can_issue_join_token` currently gates on session state + `maximum_duration_reached` only, with no separate "reconnect window" check distinct from the overall session maximum duration. This is consistent with docs/04 §7's rule being described but the concrete window value/enforcement being a mock-transport/worker-era concern (no `LiveKit`/worker exists yet in WP4 to define what "reconnect" means operationally). Reasonable deferral; recommend confirming in WP6/WP10 that a distinct reconnect-window check is added rather than silently relying on `maximum_session_ms` alone.
3. **In-memory join-token audit race.** `record_join_token_request` is a pure, immutable state transition; the actual compare-and-set race protection is provided by `try_replace`'s `expected_revision` check plus `MAX_CAS_ATTEMPTS = 3` bounded retry in `session_control.py::refresh_join_token`. In the in-memory single-process repository this is effectively safe (Python's GIL serializes the dict mutation inside `InMemorySessionRecordRepository.replace`); the theoretical race under a real concurrent-writer store (MongoDB, WP5) is explicitly a WP5 concern per docs/14 §11's "concurrent event-allocation/heartbeat" tests. Correctly deferred, not a WP4 defect.

## Resolved-ambiguity assessment (one line each)

1. **405 → 400 `INVALID_REQUEST`**: reasonable and safe — docs/04 §19's table has no dedicated code for unsupported HTTP methods, and `400` is the closest generic "unsupported request semantics" bucket; recommend accepted as-is.
2. **Join tokens allowed for `ending` sessions**: correct per docs/04 §7 ("reconnect reuses the same room ... within the approved window") — `JOINABLE_STATES` including `ENDING` matches the spec's intent that in-flight termination shouldn't strand a connected browser; accepted.
3. **Unknown `agent_config_id` → `422 agent_config_not_available`**: matches docs/04 §6 ("only an active approved agent configuration is accepted") mapped onto the `VALIDATION_FAILED` bucket with a specific field error rather than `404`; a defensible reading since the ID is a request-body field, not a path resource — accepted.
4. **Join-token response shape**: `JoinTokenData{session_id, transport}` mirrors the session-create `transport` section exactly, satisfying "scoped, short-lived ... never in a URL" without inventing a new shape — accepted.
5. **Operations/errors page sizes default 50/max 100**: docs/04 §12-§13 state no page size; reusing the turn-page bounds (which docs/04 §10 does specify) is the most conservative, internally consistent choice — accepted, documented in code comment.
6. **Feedback target rules and `reason_taxonomy_version` label**: `FeedbackContent._target_and_signal` enforces docs/04 §15's "all targets belong to the session" and "at least one feedback signal" rules precisely; `REASON_TAXONOMY_VERSION = "phase0_feedback_reasons_v1"` is a reasonable, explicit Phase 0 label per docs/02 §11 — accepted.
7. **Agent-config UI features (`partial_transcripts`, `interruptions`)**: a minimal, plausible reading of docs/04 §5's "supported UI features"; both fields are already present on the domain `AgentConfig` (`stt.partial_transcripts`, `turn_handling.interruptions_enabled`) so nothing new was invented — accepted.
8. **Extra session events with warning-only write failures**: `emit_session_event` logs a warning and does not raise when the durable event-append fails, while the session state write itself (`try_replace`) has already committed before the event is attempted — correctly keeps mutation success independent of diagnostic-event durability, consistent with docs/04 §20 ("HTTP handlers do not wait for a complete realtime conversation response") — accepted, though note this means a lost event is silently unrecoverable in this build; acceptable for Phase 0, worth revisiting once WP5 gives durable events a retry/backfill path.
9. **Host allowlist / body cap / dev-only docs**: all three independently live-verified (wrong `Host` → `403`; 64 KiB constant `MAX_REQUEST_BODY_BYTES`; `/docs` gated on `settings.app_env is AppEnvironment.DEVELOPMENT`) — accepted.
10. **Default `in_memory` persistence**: `PersistenceMode.IN_MEMORY` is the `create_app`/CLI default, matching docs/14 §22's "work packages 0-4 use mocks/local checks" cost-control sequence (no MongoDB dependency needed to pass this gate) — accepted.

## Defects (ranked)

No CRITICAL or HIGH defects found.

1. **MEDIUM — `httpx` is imported directly in test code (`backend/tests/integration/control_api/conftest.py`) but is not declared as a direct dependency anywhere in `pyproject.toml` (neither `dependencies` nor the `dev` group).** It currently resolves only because `openai`, `deepgram-sdk`, and `sarvamai` each pull in `httpx==0.28.1` transitively, so `uv.lock` happens to contain it today. This is reproducible right now (`uv sync --locked` succeeds), so it is not a blocking defect, but it violates docs/13's own stated principle ("direct dependencies are intentional, minimal, and exact... a package must correspond to an approved module or development gate") in spirit for test code: if any of those three provider SDKs ever drops its `httpx` dependency (e.g., a future OpenAI SDK major version switching HTTP clients), the test suite would silently stop resolving with no direct pin to explain why `httpx` is expected. Recommend backend-dev add `httpx` (pinned to the already-locked `0.28.1`, or the version FastAPI's own test guidance recommends) to the `dev` dependency group in a follow-up, non-blocking change. Owner: backend-dev.
2. **LOW — Reconnect-window enforcement is not distinct from `maximum_session_ms`** (see Deferred item 2 above). Not a WP4 defect; flagged so WP6/WP10 explicitly revisit it rather than it being forgotten.
3. **LOW — A failed `session_events` append (`emit_session_event`) is unrecoverable in this build** (see resolved-ambiguity item 8). Acceptable for the in-memory Phase 0 skeleton; note for WP5 to ensure the durable MongoDB event log doesn't silently drop lifecycle events without at least a retry or a countable metric.
