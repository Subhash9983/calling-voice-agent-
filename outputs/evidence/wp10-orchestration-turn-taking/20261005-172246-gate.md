### `sessionState.ts` bug-fix — read and confirmed genuine (not trivial)

Read `frontend/src/session/sessionState.ts` and `frontend/tests/session/sessionState.test.ts` diffs directly (`git diff main --`). **Before:** the `va.playback.v1` `cancelled`/`interrupted` branch only reset `agentState` and called `dropProvisionalLine(state.agentResponse)` — it never recorded which `turnId` had just been cancelled anywhere in state. The `va.transcript.v1`/`va.response.v1` branches had no knowledge of "this turn is dead" and would apply any later message carrying that same `turnId` normally. **After:** a new `cancelledTurnIds: readonly string[]` field (bounded to the most recent 20 via `addCancelledTurn`, so long sessions cannot grow it unboundedly) is populated on every cancelled/interrupted playback event, and both the transcript and response reducer branches now early-return `state` unchanged if `envelope.turnId` is already in `cancelledTurnIds`. The new test `"barge-in: a fresh user turn is attributed correctly with zero bleed-through from the cancelled prior turn"` is a genuine RED→GREEN case: it interrupts turn `tA` mid-partial-response, lets turn `tB` complete fully (transcript + response), then replays a **late** `va.response.v1`/`va.transcript.v1` for the dead `tA` and asserts the final state still shows only `tB`'s content and that every line's `turnId` is `tB`. Without the fix this would fail (the late `tA` content would append/prepend into `agentResponse`/`userTranscript`). This is a real, non-trivial fix, not a tautological test.

## Backend substance review — read, not rubber-stamped

### The Turn Manager "stays responding" bug and fix — real, traced to root cause

`backend/src/voice_agent/turn_management/turn_manager.py` is **byte-identical to `main`** (`git diff main --stat` empty) — the pure state machine itself was never broken; `agent_response_finished()` already correctly resets to idle only when called. The bug was in the **caller**: the pre-existing (unmodified-this-WP) `SttCheck._finish_turn` in `agent_worker/stt_check.py` (line ~493-495) resets `self._state` to idle via `agent_response_finished` as soon as `self._awaiting` is empty and the phase is `RESPONDING` — and the base `_accept()` method calls `self._finish_turn(...)` **immediately after handing the turn to `gate.authorize(accepted)`**, i.e. right when a transcript is handed off, regardless of whether the gate is still generating/speaking. This is exactly the bug the implementer described.

The WP10 fix lives in `agent_worker/conversation_orchestrator.py`'s `ConversationOrchestrator`, which overrides `_finish_turn`:
```python
async def _finish_turn(self, *, publish_listening: bool = True) -> None:
    if self._speaking.responding or self._awaiting:
        return  # the response (or another transcript) still owns the turn state
    await super()._finish_turn(publish_listening=publish_listening)
```
This suppresses the premature reset while the gate (`OrchestratedGate`) is still responding. The *real* reset only happens via `_on_response_done`, bound as the gate's done-listener (`gate.bind_done_listener(self._on_response_done)`), called only when the gate's turn run has genuinely settled (completed/interrupted/failed) — confirmed by reading both call sites.

**Regression test confirmed genuine, not vacuous:** `test_barge_in_during_first_audio_runs_the_canonical_order` (`backend/tests/unit/agent_worker/test_conversation_orchestrator.py:86`) explicitly waits for `_speaking(rig)` (first published audio frame) before feeding 300 ms of continuous speech "over agent audio" and asserts the interruption is accepted and the canonical cancellation order runs — i.e., barge-in succeeds *during first-audio playback*, not after a subsequent transcript arrives. This is exactly the scenario the pre-fix code would have mishandled (turn manager already reset to idle, so the VAD energy during playback would never even reach `_responding()`'s candidate-tracking logic).
