## Defects (ranked)

1. **MEDIUM — nondeterministic tie-break ordering in `provider_operations` retry listing; a real (if narrow) production correctness gap, confirmed by a genuinely flaky offline test, not a fake-only artifact.**
   `src/voice_agent/persistence/mongodb/repositories/timeline.py:206` sorts `list_for_session` by `sort=[("created_at", 1), ("operation_id", 1)]`. `operation_id` is a random UUID (`tests/support/fake_mongo.py::UuidIdGenerator`), uncorrelated with attempt order. When two attempts of the same logical request are saved within the same clock tick — which happens routinely on this Windows host, where `datetime.now(UTC)` resolution is coarse enough to tie in a tight loop — the secondary sort key decides ordering by an unrelated random value instead of by `attempt_number`. `docs/02` §19/§21's own approved index for this query, `ix_session_operations: {session_id: 1, created_at: 1}` (confirmed byte-for-byte in `tests/unit/persistence/test_design_conformance.py`), has no `operation_id` component either — the tiebreaker was a repository-only addition, not part of the approved design.
   Reproduction: `uv run pytest -q "tests/integration/persistence/test_timeline_repositories.py::test_retry_attempts_are_unique_per_logical_request" --no-cov` fails intermittently (observed 2 failures in 5 runs) with `assert [2, 1] == [1, 2]`.
   This is not purely a test-flakiness issue: any real caller of `list_for_session` (e.g., a future retry-evidence UI/report) can receive attempts out of order whenever two retries land in the same timestamp tick, which is plausible for a fast, zero-backoff retry.
   Fix: sort by `("created_at", 1), ("attempt_number", 1)` (attempt_number is already a required, monotonic field on `ProviderOperation` and is part of the collection's own unique index `uq_logical_attempt`), or add a monotonic secondary field. Owner: backend-dev.

No CRITICAL or HIGH defects found.

## Resolved-ambiguity assessment (one line each)

1. **`cache_write_tokens` — carried-over HIGH item from WP2.** The domain `UsageUnit` enum still carries `CACHE_WRITE_TOKENS` (needed by WP8/docs/08 §12,§16 and docs/15 §2.4's separate cache-write billing), but the MongoDB-boundary `StoredUsageUnit` enum in `persistence/mongodb/documents/timeline.py` (used to encode `provider_operations.usage.items[].unit`) deliberately omits it, matching docs/02 §8's literal "approved units" list — so persisting a `CACHE_WRITE_TOKENS` usage item today raises at the boundary rather than silently violating the schema. This is a safe interim resolution, but it is latent risk for WP8: once the real OpenAI adapter reports cache-write usage, every such operation's persistence write will fail with an unhandled `ValueError` inside `StoredUsageUnit(item.unit.value)` unless caught. **Recommendation: amend docs/02 §8's approved-units list to add `cache_write_tokens` before WP8 starts** (a one-line documentation change, since docs/08 and docs/15 already treat it as a real, separately-priced unit), then widen `StoredUsageUnit` to match — resolving the cross-document inconsistency at the source rather than leaving a silent trap in the persistence boundary.
2. **`readWrite`-only DB role lacks `collMod` privilege, so future validator updates cannot be applied via `apply-schema`.** `bootstrap.py::apply_schema` calls `database.command({"collMod": ..., **options})` only when an existing collection's validator no longer matches (`_validator_matches` false); in this verification run no collection was out of date, so `collMod` was never actually invoked against Atlas — this path remains **unverified** against the current grant, and MongoDB's built-in `readWrite` role does not include the `collMod` action (that requires `dbAdmin` or a custom role granting it). **Recommendation: before any future work package changes an existing collection's approved validator, either (a) grant the R&D database user a narrowly-scoped custom role adding only the `collMod` action on `voice_agent_rnd`, or (b) treat validator changes as a manual, explicitly-approved one-time Atlas-UI/script step rather than assuming `apply-schema` will succeed unattended.** Do not widen the grant to `dbAdmin` broadly without need, since the cluster is shared with another project.
3. **Create-fingerprint re-derived (not stored verbatim) for idempotent session/config creation** — reasonable: re-deriving from canonical request fields at replay time (rather than trusting a stored value) avoids a stale/tampered-fingerprint class of bug; accepted.
4. **Optional language fields on turns/consent are `None`-omittable rather than defaulted to a sentinel** — matches docs/02's "unavailable, never silently zero/empty" evidence principle applied consistently to non-numeric fields; accepted.
5. **`operation.safe_message` stored as a pointer/reference into `NormalizedFailure.safe_message` rather than duplicated** — confirmed in `domain/error_event.py:342` (`message_safe=failure.safe_message`); avoids drift between the two records; accepted.
6. **Deadlines (lease `lease_expiry`, reconcile `next_reconcile_at`) computed server-side from the write-time clock, not client-supplied** — consistent with the CAS design already reviewed; accepted.
7. **Released-lease field removal**: `release()` uses `$unset` on `worker_assignment.lease_expires_at` (confirmed `leases.py:142`) so the partial `ix_sessions_lease_due` index (`{worker_assignment.lease_expires_at: {$exists: true}}`) correctly excludes released assignments rather than requiring a sentinel/tombstone value; accepted.
8. **Retention classes and policy-version labels** (`retention_class`, `content_policy_version`, `privacy_policy_version`, `retention_policy_version` fields) are plain versioned string labels, consistent with the WP4 precedent (`REASON_TAXONOMY_VERSION`-style labeling) rather than an enum requiring a schema migration per new policy version; accepted.
9. **Half-even (banker's) rounding at 12 fractional decimal places** (`costing/cost_entries.py::_round`, `ROUND_HALF_EVEN`, `MAX_DECIMAL_PLACES = 12`) — docs/02's numeric-precision section requires "up to 12 fractional decimal places" and "round only at the final reporting boundary using the versioned calculation method" without mandating a specific rounding mode; half-even is a defensible, bias-free default and the method is recorded in the `rounding` evidence field per line, satisfying "documented rounding"; accepted.
10. **Evaluation case `input_type` as a Pydantic discriminated union tag** (`TranscriptInput`/`LiveVoiceInput`/`ReliabilityInput`, `domain/evaluation/case.py`) and **status ordering implied by transition tables analogous to `OPERATION_TRANSITIONS`** — both are minimal, schema-consistent readings of docs/16 that reuse the existing discriminated-union/state-machine idioms from earlier work packages rather than inventing new patterns; accepted.
11. **Cleanup error recording**: a failed child deletion is captured per-session in `SessionCleanupReport.failure` and surfaces in `CleanupRunReport.failures`/`to_safe_dict()` without raising, so one bad session cannot abort the whole batch and the parent is preserved for retry — matches docs/14 §11's "cleanup ... partial failure ... idempotent retry ... parent-preservation tests" requirement precisely; accepted.
