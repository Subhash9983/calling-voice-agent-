### `playbackAcks.ts` bug-fix test — read and confirmed genuine (not trivial)

Read `frontend/tests/session/playbackAcks.test.ts` and `frontend/src/session/playbackAcks.ts` side by side. The fix is real: `onPlayback()` for `cancelled`/`interrupted`/`failed` previously reset `this.active` unconditionally; it now guards with `if (this.active === null || this.active.segmentId === identity.segmentId)`, mirroring the pre-existing `completed` branch's match check. The third test case (`"ignores a cancellation for a segment that is not the currently active one"`) directly proves the regression: a `cancelled` message for a stale/foreign `segmentId` no longer wipes the timer/tracking for the segment that is genuinely still playing (asserted via `send.mock.calls` still containing `playback.progress` after the stale cancellation). This is a real RED→GREEN regression test, not a tautology.

## Deep-dive review of new/substantial test and source files

### Egress guard — genuinely DNS-level, not a no-op

`backend/tests/conftest.py`'s `sarvam_egress_attempts` fixture monkeypatches `socket.getaddrinfo` (not `httpx.HTTPTransport`/`AsyncHTTPTransport`, which is what the pre-existing OpenAI guard patches). This is the correct choke point because the `sarvamai` SDK's streaming TTS uses a raw `websockets` client, which resolves DNS via `socket.getaddrinfo` but never touches `httpx`'s transport classes — an httpx-level guard (as used for WP7/WP8) would silently pass through Sarvam's WebSocket traffic. I confirmed this is not merely asserted but genuinely tested: `backend/tests/unit/tts_adapters/sarvam/test_egress_guard.py::test_real_sdk_websocket_is_blocked_at_name_resolution` instantiates the real `SdkSarvamConnector` (the production binding, not a mock) with a fake key and calls `.open()`, driving the actual SDK connection attempt; the test asserts `SarvamTransportError` with `kind=CONNECT_FAILED` and that `sarvam_egress_attempts == ["api.sarvam.ai"]`. A second test proves the same guard also blocks a raw `httpx.Client().get(...)` to the same host (covering the SDK's REST surface). Both ran green in my full offline suite run above.

### sarvamai import confinement — confirmed via a real, content-driven boundary test

`backend/tests/unit/test_architecture_boundaries.py`'s `_ALLOWED_IMPORT_FILES["sarvamai"] = frozenset({"tts_adapters/sarvam/sdk_binding.py"})`, checked by `_uses(sarvam_binding, "sarvamai", "voice_agent.tts_adapters.sarvam")`, which scans actual file content for the import, not a hardcoded assumption. `grep -rn "sarvamai"` across `backend/src` independently confirms exactly one importing file (`tts_adapters/sarvam/sdk_binding.py`).

### Cancellation-stops-before-AudioSource — a real, not mocked, pipeline assertion

`backend/tests/integration/sarvam/test_sarvam_live.py::test_real_speech_reaches_the_audio_source_and_stops_at_interruption` (live, sarvam-marked) wires a real `SarvamTtsAdapter` with a real API key through `SpeechTurn`/`SpeechDeps` and a real `LiveKitSessionTransport` (against a `FakeGateway`/`PacedSink` standing in for the LiveKit room — the "fake room" referenced in the claim). It enqueues two segments, waits for the second segment's playback to start, then advances the cancellation fence and calls `speech.cancel()`. The assertion `assert len(sink.captured) == heard` (captured frame count before vs. after cancellation) directly proves no buffered post-cancellation audio reaches the sink that stands in for `rtc.AudioSource`. `sink.cleared >= 1` additionally confirms `clear_queue()` fired. `second.late_frames + second.stale_frames > 0` proves buffered audio existed and was dropped, not merely that nothing new arrived. The `va.playback.v1` state sequence `["started", "completed", "started", "cancelled"]` is asserted against the real `FakeGateway.sent` messages, not a mock call count.

### Text normalization — substantively tested against docs/09 intent
